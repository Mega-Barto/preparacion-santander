# Step-by-step — Ejemplos sueltos

Cada ejemplo es independiente del resto. Este documento explica qué ilustra cada uno, el orden en que leer sus archivos y cómo reproducirlo desde cero con código real del propio repositorio.

---

## Mapa de ejemplos

| Ejemplo | Stack | Puerto | BD |
|---|---|---|---|
| `postgresql-scripts` | SQL puro | — | `tasks_demo` (PostgreSQL) |
| `symfony-crud` | Symfony 6.4 + Twig + Doctrine | 8000 | `symfony_crud` |
| `springboot-crud` | Spring Boot 3 + JPA + Hibernate | 8080 | `springboot_crud` |
| `vue-app` | Vue 3 + Pinia + Vue Router | 5174 | No (JSON estático) |
| `react-app` | React 18 + Context + React Router | 5175 | No (JSON estático) |

**Orden recomendado:** SQL → Symfony → Spring Boot → Vue → React.
Subir desde la BD hacia la UI hace que cada capa tenga contexto de la anterior.

## 1. postgresql-scripts

### Qué ilustra

El ciclo completo de una BD relacional antes de meter ningún framework: diseño de tablas, inserción, consultas, relaciones, funciones PL/pgSQL y triggers.

### Preparar la BD

```powershell
psql -U postgres -c "CREATE DATABASE tasks_demo"
psql -U postgres -d tasks_demo -f 01-schema.sql
psql -U postgres -d tasks_demo -f 02-seed.sql
psql -U postgres -d tasks_demo -f 03-queries.sql
psql -U postgres -d tasks_demo -f 04-funciones.sql
```

`03-queries.sql` y `04-funciones.sql` son de lectura/objetos extra. Se pueden relanzar.

---

### Paso 1 — Esquema (`01-schema.sql`)

```sql
CREATE TABLE users (
    id    bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email varchar(180) NOT NULL UNIQUE,
    name  varchar(120) NOT NULL
);

CREATE TABLE tasks (
    id          bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title       varchar(180) NOT NULL,
    description text,
    status      varchar(20)  NOT NULL DEFAULT 'pending',
    created_at  timestamptz  NOT NULL DEFAULT now(),
    owner_id    bigint REFERENCES users (id) ON DELETE SET NULL,
    CONSTRAINT tasks_status_chk CHECK (status IN ('pending','in_progress','done'))
);

CREATE TABLE tags (
    id   bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name varchar(40) NOT NULL UNIQUE
);

CREATE TABLE task_tags (
    task_id bigint NOT NULL REFERENCES tasks (id) ON DELETE CASCADE,
    tag_id  bigint NOT NULL REFERENCES tags  (id) ON DELETE CASCADE,
    PRIMARY KEY (task_id, tag_id)
);

CREATE INDEX idx_tasks_status ON tasks (status);
CREATE INDEX idx_tasks_owner  ON tasks (owner_id);
```

**Puntos clave:**

| Elemento | Explicación |
|---|---|
| `GENERATED BY DEFAULT AS IDENTITY` | Equivalente moderno a `SERIAL`. El id lo genera la BD. `BY DEFAULT` permite insertar un id explícito si hace falta. |
| `timestamptz` | Timestamp con zona horaria. A diferencia del `TIMESTAMP WITHOUT TIME ZONE` de la integración, aquí se guarda la zona. |
| `REFERENCES users (id) ON DELETE SET NULL` | Clave foránea. Si el usuario se borra, el campo `owner_id` queda a NULL (la tarea se conserva sin dueño). |
| `ON DELETE CASCADE` en `task_tags` | Si se borra una tarea o etiqueta, se borran automáticamente sus filas en la tabla pivote. |
| `CONSTRAINT tasks_status_chk CHECK (...)` | La BD rechaza directamente cualquier valor de `status` no válido, sin depender de la aplicación. |
| `CREATE INDEX` | Acelera `WHERE status = ...` y `WHERE owner_id = ...`. En tablas pequeñas no importa; en producción sí. |

---

### Paso 2 — Consultas de referencia (`03-queries.sql`)

```sql
-- Filtro, orden y paginación
SELECT id, title, status, created_at
FROM tasks
WHERE status = 'pending'
ORDER BY created_at DESC
LIMIT 20 OFFSET 0;

-- Búsqueda sin distinguir mayúsculas (solo PostgreSQL)
SELECT id, title
FROM tasks
WHERE title ILIKE '%join%';

-- INNER JOIN: solo tareas con responsable
SELECT t.id, t.title, u.email
FROM tasks t
INNER JOIN users u ON u.id = t.owner_id;

-- LEFT JOIN: incluye tareas sin responsable (owner_id NULL)
SELECT t.id, t.title, u.email
FROM tasks t
LEFT JOIN users u ON u.id = t.owner_id;

-- Tareas sin responsable (NULL)
SELECT t.id, t.title
FROM tasks t
LEFT JOIN users u ON u.id = t.owner_id
WHERE u.id IS NULL;

-- Many-to-many: tareas con sus etiquetas
SELECT t.title, tg.name AS tag
FROM tasks t
INNER JOIN task_tags tt ON tt.task_id = t.id
INNER JOIN tags tg      ON tg.id      = tt.tag_id
ORDER BY t.title, tg.name;

-- Agregado: cuántas tareas hay por estado
SELECT status, COUNT(*) AS total
FROM tasks
GROUP BY status
ORDER BY total DESC;

-- EXISTS: usuarios con alguna tarea pendiente
SELECT u.name
FROM users u
WHERE EXISTS (
    SELECT 1 FROM tasks t
    WHERE t.owner_id = u.id AND t.status = 'pending'
);
```

**Cuándo usar INNER vs LEFT JOIN:**

| Tipo | Devuelve |
|---|---|
| `INNER JOIN` | Solo filas con coincidencia en ambas tablas |
| `LEFT JOIN` | Todas las filas de la tabla izquierda; NULL en columnas de la derecha si no hay coincidencia |

### Paso 3 — Funciones, vista y trigger (`04-funciones.sql`)

```sql
-- Función escalar: devuelve un solo valor
CREATE OR REPLACE FUNCTION count_open_tasks()
RETURNS bigint LANGUAGE sql STABLE
AS $$
    SELECT COUNT(*) FROM tasks WHERE status <> 'done';
$$;

-- Función que devuelve filas (SETOF)
CREATE OR REPLACE FUNCTION tasks_by_status(p_status text)
RETURNS SETOF tasks LANGUAGE sql STABLE
AS $$
    SELECT * FROM tasks WHERE status = p_status ORDER BY created_at DESC;
$$;

-- Vista: consulta con nombre reutilizable
CREATE OR REPLACE VIEW open_tasks AS
SELECT id, title, status, created_at, owner_id
FROM tasks
WHERE status <> 'done';

-- Trigger: registra cada cambio de estado en un log
CREATE OR REPLACE FUNCTION log_task_status()
RETURNS trigger LANGUAGE plpgsql
AS $$
BEGIN
    IF NEW.status IS DISTINCT FROM OLD.status THEN
        INSERT INTO task_status_log (task_id, old_status, new_status)
        VALUES (NEW.id, OLD.status, NEW.status);
    END IF;
    RETURN NEW;
END;
$$;

DROP TRIGGER IF EXISTS trg_log_task_status ON tasks;

CREATE TRIGGER trg_log_task_status
AFTER UPDATE OF status ON tasks
FOR EACH ROW
EXECUTE FUNCTION log_task_status();
```

**Diferencias entre los tipos de función:**

| Tipo | Sintaxis | Devuelve |
|---|---|---|
| Función SQL | `LANGUAGE sql` + `$$` SELECT ... `$$` | Valor o conjunto de filas |
| Función PL/pgSQL | `LANGUAGE plpgsql` + `BEGIN … END` | Control de flujo, variables, excepciones |
| Función trigger | `RETURNS trigger` + `RETURN NEW/OLD` | La fila modificada (o NULL para cancelar) |

**`IS DISTINCT FROM`:** a diferencia de `<>`, funciona correctamente cuando alguno de los valores es NULL (`NULL <> NULL` es NULL en SQL, no TRUE).

## 2. symfony-crud

### Qué ilustra

CRUD con formularios HTML renderizados en el servidor (Twig). Sin API. Es la forma "clásica" de Symfony antes de pasar a arquitectura REST. La misma entidad `Task` que usa la integración, pero con controlador HTML en lugar de JSON.

### Arrancar

```powershell
psql -U postgres -c "CREATE DATABASE symfony_crud"
cd ejemplos/symfony-crud
composer install
php bin/console doctrine:migrations:migrate --no-interaction
symfony server:start   # o: php -S localhost:8000 -t public
```

Abre `http://127.0.0.1:8000/tasks`.

---

### Paso 1 — Entidad (`src/Entity/Task.php`)

La entidad es idéntica a la de `integracion/backend`. Ver los detalles en `integracion/step-by-step.md § Fase 2`.

```php
#[ORM\Entity(repositoryClass: TaskRepository::class)]
#[ORM\Table(name: 'tasks')]
class Task
{
    #[ORM\Id]
    #[ORM\GeneratedValue(strategy: 'IDENTITY')]
    #[ORM\Column]
    private ?int $id = null;

    #[ORM\Column(length: 180)]
    #[Assert\NotBlank]
    #[Assert\Length(max: 180)]
    private string $title = '';

    #[ORM\Column(type: 'text', nullable: true)]
    private ?string $description = null;

    #[ORM\Column(length: 20)]
    #[Assert\Choice(choices: ['pending', 'in_progress', 'done'])]
    private string $status = 'pending';

    #[ORM\Column]
    private \DateTimeImmutable $createdAt;

    public function __construct() {
        $this->createdAt = new \DateTimeImmutable();
    }
    // … getters y setters …
}
```

### Paso 2 — Formulario (`src/Form/TaskType.php`)

```php
class TaskType extends AbstractType
{
    public function buildForm(FormBuilderInterface $builder, array $options): void
    {
        $builder
            ->add('title',       TextType::class,     ['label' => 'Título'])
            ->add('description', TextareaType::class, ['label' => 'Descripción', 'required' => false])
            ->add('status',      ChoiceType::class,   [
                'label'   => 'Estado',
                'choices' => [
                    'Pendiente' => 'pending',
                    'En curso'  => 'in_progress',
                    'Hecha'     => 'done',
                ],
            ])
            ->add('save', SubmitType::class, ['label' => 'Guardar']);
    }

    public function configureOptions(OptionsResolver $resolver): void
    {
        $resolver->setDefaults(['data_class' => Task::class]);
    }
}
```

- `data_class: Task::class` liga el formulario a la entidad. Los nombres de los campos (`title`, `description`, `status`) deben coincidir con los getters/setters de la entidad.
- `ChoiceType` genera un `<select>`. Las claves son las etiquetas visibles; los valores son lo que se guarda.
- Symfony añade automáticamente un token CSRF oculto en cada formulario.

---

### Paso 3 — Controlador HTML (`src/Controller/TaskController.php`)

**Listar:**
```php
#[Route('/tasks', name: 'task_index', methods: ['GET'])]
public function index(TaskRepository $tasks): Response
{
    return $this->render('task/index.html.twig', [
        'tasks' => $tasks->findLatest(),
    ]);
}
```

**Crear (GET + POST en la misma acción):**
```php
#[Route('/tasks/new', name: 'task_new', methods: ['GET', 'POST'])]
public function new(Request $request, EntityManagerInterface $em): Response
{
    $task = new Task();
    $form = $this->createForm(TaskType::class, $task);
    $form->handleRequest($request);           // enlaza el POST a la entidad

    if ($form->isSubmitted() && $form->isValid()) {
        $em->persist($task);
        $em->flush();
        $this->addFlash('success', 'Tarea creada');
        return $this->redirectToRoute('task_show', ['id' => $task->getId()]);
    }

    return $this->render('task/form.html.twig', [
        'form'  => $form,
        'title' => 'Nueva tarea',
    ]);
}
```

**Ciclo GET/POST de un formulario Symfony:**

```
GET  /tasks/new  → createForm(TaskType, new Task())
                 → render('form.html.twig', form vacío)
POST /tasks/new  → handleRequest($request) rellena la entidad desde $_POST
                 → isSubmitted() = true (llegó por POST)
                 → isValid() = true si pasan los Assert
                 → persist + flush + flash + redirect
```

**Borrar con CSRF:**
```php
#[Route('/tasks/{id}/delete', methods: ['POST'])]
public function delete(Task $task, Request $request, EntityManagerInterface $em): Response
{
    if ($this->isCsrfTokenValid('delete'.$task->getId(), $request->request->get('_token'))) {
        $em->remove($task);
        $em->flush();
    }
    return $this->redirectToRoute('task_index');
}
```

- El borrado usa `POST`, no `DELETE`, porque los formularios HTML solo admiten GET y POST.
- `isCsrfTokenValid` verifica el token oculto que el formulario Twig incluye automáticamente.

### Paso 4 — Migración (`migrations/Version20241110000000.php`)

La migración la genera Doctrine a partir de la entidad:

```powershell
php bin/console make:entity Task      # si la entidad no existiera aún
php bin/console make:migration        # genera el archivo en migrations/
php bin/console doctrine:migrations:migrate
```

Si la tabla ya existe (por haber cargado `database/init.sql`), la migración detecta que no hay cambios y no hace nada.

**Plan B si la migración falla:**
```powershell
psql -U postgres -d symfony_crud -f database/init.sql
```

### Diferencia clave con integracion/backend

| symfony-crud | integracion/backend |
|---|---|
| `$this->render('template.twig', [...])` | `$this->json($data)` |
| `createForm(TaskType::class, $task)` | `json_decode($request->getContent(), true)` |
| `handleRequest()` + `isValid()` | `validate()` + comprobación manual |
| `addFlash('success', '...')` | Código HTTP 201 / 422 |
| `redirectToRoute(...)` | No redirige nunca |
| Token CSRF en formulario | Sin sesión |

## 3. springboot-crud

### Qué ilustra

La misma API REST que la integración, pero en Java. Comparar Spring Boot con Symfony aclara qué es el lenguaje y qué es la arquitectura.

### Arrancar

```powershell
psql -U postgres -c "CREATE DATABASE springboot_crud"
cd ejemplos/springboot-crud
mvn spring-boot:run
```

Hibernate creará la tabla automáticamente al arrancar.

---

### Paso 1 — application.properties

```properties
server.port=8080

spring.datasource.url=jdbc:postgresql://localhost:5432/springboot_crud
spring.datasource.username=postgres
spring.datasource.password=postgres

spring.jpa.hibernate.ddl-auto=update        # crea/actualiza la tabla al arrancar
spring.jpa.open-in-view=false               # evita lazy loading fuera de la transacción
spring.jpa.show-sql=true                    # imprime el SQL en consola (útil para debug)
spring.jpa.properties.hibernate.dialect=org.hibernate.dialect.PostgreSQLDialect
```

- `ddl-auto=update` equivale a "haz `make:migration` + `migrate` automáticamente". No apto para producción (usar `validate` allí).
- `open-in-view=false` es la práctica recomendada: fuerza que todas las consultas ocurran dentro de la capa de servicio.

---

### Paso 2 — Entidad (`model/Task.java`)

```java
@Entity
@Table(name = "tasks")
public class Task {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @NotBlank
    @Size(max = 180)
    @Column(nullable = false, length = 180)
    private String title;

    @Column(columnDefinition = "text")
    private String description;

    @Pattern(regexp = "pending|in_progress|done")
    @Column(nullable = false, length = 20)
    private String status = "pending";

    @Column(nullable = false, updatable = false)
    private Instant createdAt = Instant.now();   // se inicializa al construir, updatable=false lo protege
}
```

- `updatable = false` en `createdAt` hace que Hibernate ignore este campo en los `UPDATE`. Equivale al constructor PHP que no tiene setter.
- `Instant` es la clase Java equivalente a `\DateTimeImmutable` de PHP: inmutable y en UTC.
- `@Pattern(regexp = "...")` equivale a `#[Assert\Choice]` de Symfony.

**Equivalencia PHP ↔ Java:**

| PHP (Symfony) | Java (Spring Boot) |
|---|---|
| `#[ORM\Entity]` | `@Entity` |
| `#[ORM\Column(length: 180)]` | `@Column(nullable = false, length = 180)` |
| `#[Assert\NotBlank]` | `@NotBlank` |
| `#[Assert\Length(max: 180)]` | `@Size(max = 180)` |
| `#[Assert\Choice(choices: [...])]` | `@Pattern(regexp = "...")` |
| `\DateTimeImmutable` | `Instant` |

---

### Paso 3 — Repository (`repository/TaskRepository.java`)

```java
public interface TaskRepository extends JpaRepository<Task, Long> {
    List<Task> findAllByOrderByCreatedAtDesc();
}
```

- `JpaRepository` hereda `findById`, `save`, `delete`, `findAll`, etc.
- `findAllByOrderByCreatedAtDesc` es un **derived query**: Spring Data genera el SQL a partir del nombre del método. No hace falta escribir ninguna consulta.

**Equivalencia Symfony:**

| Symfony | Spring Boot |
|---|---|
| `extends ServiceEntityRepository` | `extends JpaRepository<Task, Long>` |
| `findBy([], ['createdAt' => 'DESC'])` | `findAllByOrderByCreatedAtDesc()` |
| `find($id)` | `findById(id).orElseThrow(...)` |
| `$em->persist($task); $em->flush()` | `repository.save(task)` |
| `$em->remove($task); $em->flush()` | `repository.delete(task)` |

---

### Paso 4 — Servicio (`service/TaskService.java`)

```java
@Service
public class TaskService {

    private final TaskRepository tasks;

    public TaskService(TaskRepository tasks) {
        this.tasks = tasks;  // inyección por constructor (sin @Autowired)
    }

    public List<Task> findAll() {
        return tasks.findAllByOrderByCreatedAtDesc();
    }

    public Task findById(Long id) {
        return tasks.findById(id)
                    .orElseThrow(() -> new TaskNotFoundException(id));
    }

    @Transactional
    public Task create(Task input) {
        Task task = new Task();                 // nueva entidad limpia
        task.setTitle(input.getTitle());
        task.setDescription(input.getDescription());
        task.setStatus(input.getStatus() == null || input.getStatus().isBlank()
                       ? "pending" : input.getStatus());
        return tasks.save(task);
    }

    @Transactional
    public Task update(Long id, Task input) {
        Task current = findById(id);            // lanza 404 si no existe
        current.setTitle(input.getTitle());
        current.setDescription(input.getDescription());
        current.setStatus(input.getStatus());
        return tasks.save(current);
    }

    @Transactional
    public void delete(Long id) {
        tasks.delete(findById(id));
    }
}
```

- La capa de servicio aísla la lógica de negocio del controlador. El controlador solo mapea HTTP → servicio → respuesta.
- `@Transactional` garantiza que si algo falla a mitad de la operación, se hace rollback automático.
- No se crea una `Task` nueva en `update`: se recupera la existente y se modifican sus campos. El `save` sobre una entidad ya persistida genera un `UPDATE`.

---

### Paso 5 — Controlador (`controller/TaskController.java`)

```java
@RestController
@RequestMapping("/api/tasks")
public class TaskController {

    private final TaskService tasks;

    public TaskController(TaskService tasks) { this.tasks = tasks; }

    @GetMapping
    public List<Task> list() { return tasks.findAll(); }

    @GetMapping("/{id}")
    public Task show(@PathVariable Long id) { return tasks.findById(id); }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)           // 201
    public Task create(@Valid @RequestBody Task task) { return tasks.create(task); }

    @PutMapping("/{id}")
    public Task update(@PathVariable Long id, @Valid @RequestBody Task task) {
        return tasks.update(id, task);
    }

    @DeleteMapping("/{id}")
    @ResponseStatus(HttpStatus.NO_CONTENT)        // 204
    public void delete(@PathVariable Long id) { tasks.delete(id); }
}
```

- `@RestController` = `@Controller` + `@ResponseBody`. Todo lo que devuelva un método se serializa a JSON automáticamente.
- `@Valid` en el parámetro `@RequestBody` activa las anotaciones de validación de la entidad (`@NotBlank`, `@Size`, `@Pattern`).
- `@ResponseStatus` sobreescribe el 200 por defecto. Sin él, `create` devolvería 200 en lugar de 201.

---

### Paso 6 — Manejo global de errores (`controller/ApiExceptionHandler.java`)

```java
@RestControllerAdvice
public class ApiExceptionHandler {

    @ExceptionHandler(TaskNotFoundException.class)
    @ResponseStatus(HttpStatus.NOT_FOUND)                      // 404
    public Map<String, String> notFound(TaskNotFoundException ex) {
        return Map.of("error", ex.getMessage());
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    @ResponseStatus(HttpStatus.BAD_REQUEST)                    // 400
    public Map<String, String> invalid(MethodArgumentNotValidException ex) {
        String message = ex.getBindingResult().getFieldErrors().stream()
            .map(e -> e.getField() + ": " + e.getDefaultMessage())
            .findFirst()
            .orElse("Invalid payload");
        return Map.of("error", message);
    }
}
```

- `@RestControllerAdvice` intercepta excepciones lanzadas en **cualquier** controlador. Equivale a un handler global.
- `MethodArgumentNotValidException` la lanza Spring automáticamente cuando `@Valid` falla.
- En Symfony el equivalente sería un `kernel.exception` event listener o un `ExceptionSubscriber`.

## 4. vue-app

### Qué ilustra

Vue 3 con Composition API, Pinia y Vue Router **sin backend real**. Los datos se cargan desde `public/tasks.json`; crear, editar y borrar viven en memoria y se pierden al recargar. Ideal para practicar la UI sin depender de Symfony.

### Arrancar

```powershell
cd ejemplos/vue-app
npm install
npm run dev   # → http://127.0.0.1:5174
```

---

### Paso 1 — Cliente HTTP (`src/api/client.js`)

```js
const baseURL = import.meta.env.VITE_API_URL || ''

export async function fetchTasks() {
  const response = await fetch(`${baseURL}/tasks.json`)
  if (!response.ok) throw new Error(`HTTP ${response.status}`)
  return response.json()
}
```

- Sin `VITE_API_URL` en `.env`, `baseURL` es vacío y `fetch('/tasks.json')` carga el archivo de `public/`.
- Con `VITE_API_URL=http://127.0.0.1:8000`, el mismo código llamaría a `http://127.0.0.1:8000/tasks.json`. Para conectar a la integración solo habría que cambiar `fetchTasks` por las llamadas de la API REST.

---

### Paso 2 — Store Pinia (`src/stores/tasks.js`)

```js
export const useTaskStore = defineStore('tasks', () => {
  const items   = ref([])
  const loading = ref(false)
  const error   = ref('')
  let nextId = 1   // contador local porque no hay BD que genere ids

  const pendingCount = computed(
    () => items.value.filter(t => t.status !== 'done').length
  )

  async function fetchAll() {
    loading.value = true
    try {
      items.value = await fetchTasks()
      nextId = items.value.reduce((max, t) => Math.max(max, t.id), 0) + 1
    } catch (e) {
      error.value = e.message
    } finally {
      loading.value = false
    }
  }

  function create(payload) {
    const task = {
      id:          nextId++,             // id local incremental
      title:       payload.title,
      description: payload.description || '',
      status:      payload.status || 'pending',
      createdAt:   new Date().toISOString()
    }
    items.value.unshift(task)
    return task
  }

  function update(id, payload) {
    const current = items.value.find(t => t.id === Number(id))
    if (!current) return null
    Object.assign(current, payload)    // muta la referencia; Vue detecta el cambio
    return current
  }

  function remove(id) {
    items.value = items.value.filter(t => t.id !== Number(id))
  }

  return { items, loading, error, pendingCount, fetchAll, create, update, remove }
})
```

**Diferencia con `integracion/frontend-vue`:**

| vue-app (sin API) | integracion/frontend-vue |
|---|---|
| `create` / `update` son síncronos | Son `async`, llaman a `api.create/update` |
| `nextId` es un contador local | El id lo devuelve el servidor en el JSON |
| `Object.assign(current, payload)` | Reemplaza la posición en el array con la respuesta del servidor |

### Paso 4 — Vistas

**TaskList.vue — puntos clave:**

```vue
<script setup>
const store = useTaskStore()
const { items, loading } = storeToRefs(store)  // reactividad preservada
onMounted(() => store.fetchAll())
</script>

<template>
  <p v-if="loading">Cargando…</p>
  <p v-else-if="items.length === 0">No hay tareas.</p>
  <table v-else>
    <tr v-for="task in items" :key="task.id">
      <td><RouterLink :to="{ name: 'task-detail', params: { id: task.id } }">{{ task.title }}</RouterLink></td>
      <td>{{ task.status }}</td>
      <td><button @click="store.remove(task.id)">Borrar</button></td>
    </tr>
  </table>
</template>
```

- `v-if` / `v-else-if` / `v-else` comparten el mismo "bloque" condicional. Solo se renderiza uno.
- `:to="{ name: 'task-detail', params: { id: task.id } }"` navega por nombre, no por URL. Si la URL cambia, el enlace no se rompe.

**TaskForm.vue — v-model en formulario:**

```vue
<script setup>
const form = reactive({ title: '', description: '', status: 'pending' })

async function onSubmit() {
  await store.create({ ...form })   // spread: pasa un POJO, no el Proxy reactivo
  router.push({ name: 'tasks' })
}
</script>

<template>
  <form @submit.prevent="onSubmit">
    <input v-model.trim="form.title" required maxlength="180" />
    <textarea v-model="form.description" />
    <select v-model="form.status">
      <option value="pending">Pendiente</option>
      <option value="in_progress">En curso</option>
      <option value="done">Hecha</option>
    </select>
    <button type="submit">Guardar</button>
  </form>
</template>
```

- `reactive()` crea un objeto reactivo completo. Útil para agrupar campos relacionados.
- `v-model.trim` en un `<input>` elimina espacios al inicio y al final antes de sincronizar.
- `{ ...form }` crea una copia plana. Evita pasar el objeto Proxy de Vue al store.

### Paso 2 — Context + Reducer (`src/state/TaskContext.jsx`)

```jsx
function taskReducer(state, action) {
  switch (action.type) {
    case 'loading': return { ...state, loading: true,  error: '' }
    case 'loaded':  return { ...state, loading: false, items: action.items }
    case 'created': return { ...state, items: [action.item, ...state.items] }
    case 'updated': return { ...state, items: state.items.map(t => t.id === action.item.id ? action.item : t) }
    case 'removed': return { ...state, items: state.items.filter(t => t.id !== action.id) }
    case 'failed':  return { ...state, loading: false, error: action.error }
    default:        return state
  }
}
```

- `useReducer` en lugar de múltiples `useState` independientes. Centraliza todas las transiciones.
- Cada case devuelve un objeto nuevo (`{ ...state, ... }`). **Nunca se muta el estado anterior**.

```jsx
export function TaskProvider({ children }) {
  const [state, dispatch] = useReducer(taskReducer, initialState)

  async function fetchAll() {
    dispatch({ type: 'loading' })
    try   { dispatch({ type: 'loaded',  items: await list() }) }
    catch (e) { dispatch({ type: 'failed',  error: e.message }) }
  }

  function create(payload) {
    const maxId = state.items.reduce((max, t) => Math.max(max, t.id), 0)
    const item = {
      id:          maxId + 1,
      title:       payload.title,
      description: payload.description || '',
      status:      payload.status || 'pending',
      createdAt:   new Date().toISOString()
    }
    dispatch({ type: 'created', item })
    return item
  }

  function update(id, payload) {
    const current = state.items.find(t => t.id === id)
    if (!current) return null
    const item = { ...current, ...payload }  // fusiona con spread (no muta)
    dispatch({ type: 'updated', item })
    return item
  }

  function remove(id) {
    dispatch({ type: 'removed', id })
  }

  useEffect(() => { fetchAll() }, [])   // carga al montar

  return (
    <TaskContext.Provider value={{ ...state, fetchAll, create, update, remove }}>
      {children}
    </TaskContext.Provider>
  )
}
```

**Diferencia con `integracion/frontend-react`:**

| react-app (sin API) | integracion/frontend-react |
|---|---|
| `create` / `update` son síncronos | Son `async` y llaman a `taskService` |
| `id = maxId + 1` local | El id viene del servidor |
| `{ ...current, ...payload }` fusiona localmente | `updated` llega del servidor con todos los campos |

### Paso 3 — Páginas

**TaskListPage.jsx — iteración y select controlado:**

```jsx
export function TaskListPage() {
  const { items, loading, update, remove } = useTasks()

  if (loading && items.length === 0) return <p>Cargando…</p>

  return (
    <table>
      <tbody>
        {items.map(task => (
          <tr key={task.id}>
            <td>{task.title}</td>
            <td>
              <select value={task.status}
                      onChange={e => update(task.id, { status: e.target.value })}>
                <option value="pending">Pendiente</option>
                <option value="in_progress">En curso</option>
                <option value="done">Hecha</option>
              </select>
            </td>
            <td><button onClick={() => remove(task.id)}>Borrar</button></td>
          </tr>
        ))}
      </tbody>
    </table>
  )
}
```

- `key={task.id}` en el `<tr>` es obligatorio. React lo usa para reconciliar el DOM virtual: sin `key` puede reubicar filas incorrectamente al reordenar o borrar.
- El `select` es **controlado**: `value={task.status}` fija el estado visible; `onChange` lo actualiza. Sin el `onChange`, el select sería de solo lectura.

**TaskFormPage.jsx — formulario controlado con un solo handler:**

```jsx
export function TaskFormPage() {
  const { create } = useTasks()
  const navigate = useNavigate()
  const [form, setForm] = useState({ title: '', description: '', status: 'pending' })

  function updateField(event) {
    const { name, value } = event.target
    setForm(current => ({ ...current, [name]: value }))  // computed property name
  }

  async function handleSubmit(event) {
    event.preventDefault()
    await create(form)
    navigate('/tasks')
  }

  return (
    <form onSubmit={handleSubmit}>
      <input    name="title"       value={form.title}       onChange={updateField} required maxLength={180} />
      <textarea name="description" value={form.description} onChange={updateField} />
      <select   name="status"      value={form.status}      onChange={updateField}>
        <option value="pending">Pendiente</option>
        <option value="in_progress">En curso</option>
        <option value="done">Hecha</option>
      </select>
      <button type="submit">Guardar</button>
    </form>
  )
}
```

- `[name]: value` es "computed property name" de ES6: la clave del objeto es dinámica, tomada del atributo `name` del elemento del formulario. Un único `updateField` sirve para todos los inputs.
- `setForm(current => ...)` usa la forma funcional para evitar condiciones de carrera si hay múltiples actualizaciones rápidas.
